1.5 Existing CI/CD State

What Exists (from upstream Moodle)

  • .github/workflows/push.yml — Grunt lint + PHPUnit (MySQL 8.4 + PostgreSQL 14)
  • .github/workflows/config-template.php — CI config template for test environments
  • .github/workflows/close-pull-requests.yml — Auto-close PRs to protected branches
  • .github/workflows/onebyone.yml / windows.yml — Matrix test workflows

What Does NOT Exist

  • ❌ No deployment pipeline
  • ❌ No staging/production environment separation
  • ❌ No custom plugin testing
  • ❌ No frontend build pipeline for custom plugins
  • ❌ No artifact management
  • ❌ No rollback mechanism
  • ❌ No security scanning
  • ❌ No secrets management (passwords hardcoded in config.php)
  • ❌ No health checks or smoke tests
  • ❌ No monitoring or alerting integration

1.7 Architectural Risks & Problems

Deployment Risks

  1. Manual deployment — No automated deployment process; changes are likely pushed directly to the server via SSH/git pull
  2. No rollback capability — If a deployment breaks production, there's no automated way to revert
  3. Submodule complexity — 3 Git submodules (veda, codingplayground, coursedashboard) pointing to separate repos; version pinning is fragile
  4. No database migration safety — Moodle upgrade runs upgrade.php which is destructive and non-reversible
  5. Coupled microservices — Veda FastAPI, Judge0, Next.js all on localhost — single server architecture with no failover

Development Risks

  1. No branch protection — Nothing prevents force-pushes or direct commits to main
  2. No code review enforcement — No required reviewers on PRs
  3. ALPHA maturity plugins in production — Veda, Coding Playground, and Course Dashboard are all marked MATURITY_ALPHA
  4. No automated testing for custom plugins — PHPUnit config only covers Moodle core test suites
  5. Frontend builds not in CI — dist/ folders are committed as build artifacts rather than built in pipeline

Scalability Risks

  1. Single-server architecture — All services (Moodle, Redis, MySQL, FastAPI, Judge0, Next.js) on one machine
  2. No CDN — Static assets served directly from the application server
  3. No load balancing — Redis sessions are local; no session sharing across multiple web servers
  4. No cron monitoring — Moodle cron jobs run without supervision or alerting
